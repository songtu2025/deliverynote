# 管理员维护与库位/排仓资料维护设计

- 日期：2026-07-21
- 状态：用户已确认
- 目标终端：PC，主要视口宽度 1280–1920px
- 设计依据：当前线上界面、现有 FastAPI/React 调用链和库位数据业务逻辑

## 1. 背景与问题

当前“管理员维护 / 输入资料”同时展示五张状态卡、一个通用上传表单和一张混合历史表。用户需要先理解三套信息结构，才能判断某类资料是否可用、当前维护了什么以及下一步应做什么。

“库位/排仓数据”尤其不直观：页面只展示版本名和文件名，没有解释数据用途、必要字段、覆盖范围、实际内容和质量问题。当前启用版本 `position-linux-acceptance` 只有 1 行，覆盖 1 个站点、1 个积加 SKU 和 1 个 MSKU，但这些信息在页面中不可见。

现有库位/排仓数据不参与采购余额扣减或仓库分配。它在导出阶段按“店铺-站点＋积加 SKU”匹配待处理数据，并补充“规模定位、备货定位、已下单可售天数”。同一键存在多个 MSKU 时，MSKU 必须非空且唯一。

本轮审计截图保存在 `design/audit-admin-current/`：

1. `01-input-versions-desktop.png`：输入资料结构割裂，通用上传入口与具体资料类型脱节。
2. `02-users-desktop.png`：用户管理基本可用，但页面空间利用率低，角色和危险操作说明较弱。
3. `03-create-user-modal.png`：表单结构清楚，但取消按钮仍为英文，角色说明不足。
4. `04-audit-log-desktop.png`：记录可读，但缺少筛选、详情和更友好的对象名称。
5. `05-input-versions-mobile.png`：移动端能够重排，但本轮已明确不作为设计目标。

## 2. 目标

1. 管理员进入页面后能立即知道五类基础资料是否就绪、当前版本和更新时间。
2. 每类资料都有独立、明确的用途说明、内容摘要、预览、下载、替换和版本记录。
3. 库位/排仓资料同时支持网页逐条维护和 Excel 整表替换。
4. 所有修改先进入服务器草稿，只有发布才生成并启用正式版本。
5. 草稿跨刷新、退出登录和更换电脑保留，不影响当前正式数据和已创建批次。
6. 保持现有批次锁定版本、业务字段、核心匹配逻辑和 Excel 工作表格式不变。

## 3. 非目标

- 不为采购、商品、供应商和导出模板增加网页逐条增删改。
- 不修改采购匹配、仓库优先级、数量守恒、拆分或导出 A:G 字段。
- 不让历史批次自动切换到新版本。
- 不做移动端专门布局和交互优化。
- 不引入 Redis、Celery、独立微服务或新的前端状态框架。

## 4. PC 信息架构

管理员维护保留三个一级区域：基础资料、用户账号、操作记录。

“基础资料”使用左右分栏：

- 左侧 280px 左右的资料目录固定展示采购需求、商品信息、供应商资料、库位/排仓和导出模板。
- 每项展示就绪状态、当前版本和最后更新时间。
- 右侧使用剩余宽度展示所选资料的用途、状态、内容和操作。
- 页面不再同时堆叠五张状态卡、通用上传表单和所有类型的混合历史表。

其他四类资料的右侧详情包含：

- 资料用途和影响范围。
- 当前启用版本、上传时间、创建人和文件名。
- 行数或模板结构等摘要。
- 内容预览。
- 下载当前文件、上传替换、查看历史版本和启用历史版本。

库位/排仓详情额外包含：

- 行数、站点数、积加 SKU 数、MSKU 数、错误数和警告数。
- 当前数据与版本记录两个视图。
- 搜索、站点筛选、规模定位筛选、仅看错误、仅看已修改。
- 下载当前版本、Excel 整表替换、开始或继续网页维护。

## 5. 库位/排仓网页维护

### 5.1 表格

表格固定展示：

1. 店铺-站点
2. 积加 SKU
3. MSKU
4. 规模定位
5. 备货定位
6. 已下单可售天数
7. 修改状态
8. 操作

顶部固定操作栏展示草稿状态、最后保存时间、修改数量、错误数量，并提供新增、导入 Excel、下载草稿、放弃草稿和发布按钮。

新增或编辑使用右侧面板。面板提供字段解释、示例、即时校验和保存按钮。表格支持复制一行、删除单行、批量删除和撤销本次未保存编辑。

### 5.2 草稿行为

- 同一资料类型只允许存在一个进行中的服务器草稿。
- 点击“开始维护”时，从当前启用版本复制出草稿；已有草稿时直接继续。
- 新增、编辑、复制和删除记录后立即保存到服务器草稿。
- 页面展示最后编辑人、最后更新时间和修订号。
- 草稿刷新页面、退出登录或更换电脑后仍存在。
- 放弃草稿需要二次确认，放弃后正式版本保持不变。

### 5.3 Excel 整表替换

- Excel 必须包含 `MSKU_视图` 工作表及现有六个字段。
- 上传文件先在服务器解析和校验，不直接启用。
- 界面展示相对当前草稿的新增、修改、删除、错误和警告数量。
- 用户确认后，上传内容完整替换草稿；任何解析或保存失败都保留原草稿。
- 管理员可以在发布前继续用网页逐条修正导入后的内容。

### 5.4 发布

- 发布前再次执行全量校验。
- 存在错误时禁止发布；只有警告时允许管理员确认继续。
- 发布时生成新的 `MSKU_视图` Excel，创建新的 `InputVersion`，停用旧版本并启用新版本。
- 版本名称由管理员确认，默认值使用日期时间。
- 已有批次继续使用创建时锁定的旧版本，新版本只影响之后创建的批次。
- 发布成功后草稿标记为已发布，不再接受修改。

## 6. 校验与提示

阻止发布的错误：

- 缺少 `MSKU_视图` 或六个必要字段。
- 店铺-站点或积加 SKU 为空。
- 同一“店铺-站点＋积加 SKU”存在多行，但 MSKU 为空或重复。
- 文件无法解析、包含完全重复记录或草稿保存不完整。

允许确认后发布的警告：

- 规模定位不是“短尾、中尾、长尾”。
- 已下单可售天数不是常见数字格式。
- 备货定位为空。
- 数据量、站点数或 SKU 数相对当前版本出现显著变化。

错误和警告都必须显示总数、原因和可定位的行号。发布窗口汇总新增、修改、删除、错误和警告数量。

## 7. 服务端数据设计

新增 `input_drafts`：

- `id`
- `kind`
- `base_version_id`
- `status`：editing、published、discarded
- `revision`
- `created_by`、`updated_by`
- `created_at`、`updated_at`

同一 `kind` 只允许一个 `editing` 草稿。

新增 `position_draft_rows`：

- `id`
- `draft_id`
- `row_order`
- 六个现有库位/排仓字段
- `created_at`、`updated_at`

草稿表是维护层，不参与计算和导出。正式批次仍只读取 `InputVersion.storage_path` 指向的 Excel 文件，从而保持 Web、CLI 和 Worker 共用现有核心逻辑。

## 8. API 设计

通用资料查看：

- `GET /api/input-versions/{version_id}/summary`
- `GET /api/input-versions/{version_id}/preview`
- `GET /api/input-versions/{version_id}/download`

库位草稿：

- `POST /api/input-drafts/position`：创建或返回进行中草稿
- `GET /api/input-drafts/position`：读取草稿摘要
- `GET /api/input-drafts/{draft_id}/rows`：分页、搜索和筛选
- `POST /api/input-drafts/{draft_id}/rows`：新增
- `PUT /api/input-drafts/{draft_id}/rows/{row_id}`：修改
- `DELETE /api/input-drafts/{draft_id}/rows/{row_id}`：删除
- `POST /api/input-drafts/{draft_id}/rows/bulk-delete`：批量删除
- `POST /api/input-drafts/{draft_id}/import-preview`：解析 Excel 并返回差异
- `POST /api/input-drafts/{draft_id}/import-apply`：确认整表替换草稿
- `GET /api/input-drafts/{draft_id}/download`：下载草稿
- `POST /api/input-drafts/{draft_id}/validate`：全量校验
- `POST /api/input-drafts/{draft_id}/publish`：生成并启用新版本
- `POST /api/input-drafts/{draft_id}/discard`：放弃草稿

所有写接口仅管理员可用，并要求客户端提交当前 `revision`。修订号不一致时返回 409，页面提示其他管理员已经修改并要求刷新。

## 9. 原子性与错误恢复

- 单行写操作与修订号更新在同一数据库事务中完成。
- Excel 导入先解析到临时数据，校验完成后一次性替换草稿行。
- 发布先生成临时 Excel，再在数据库事务中创建正式版本、切换启用状态、写审计记录并标记草稿。
- 数据库事务失败时删除临时或目标文件，正式版本保持不变。
- 文件生成失败时不写入正式版本记录。
- 前端离开存在未提交表单的编辑面板时提示确认；已经保存到服务器的草稿不需要额外提示。

## 10. 操作记录

记录以下关键动作：

- 创建或继续草稿
- Excel 导入草稿
- 放弃草稿
- 发布新版本
- 启用历史版本

不记录每次键盘输入。单行保存通过草稿的最后编辑人和更新时间追踪，避免操作记录被大量自动保存事件淹没。

## 11. 测试与验收

后端测试：

- 从当前版本创建草稿，正式文件不变。
- 草稿跨请求和重新登录保留。
- 单行新增、编辑、复制和删除正确更新修订号。
- 旧修订号写入返回 409。
- Excel 整表替换正确计算新增、修改和删除。
- 错误文件不会破坏原草稿。
- 校验能定位缺失键和重复 MSKU。
- 发布生成可被现有 `read_position_workbook` 读取的 Excel。
- 发布后只有新版本启用，旧批次仍引用旧版本。
- 发布失败不留下半成品版本或文件。

前端测试：

- 资料目录和所选资料详情同步。
- 当前库位数据摘要、预览和版本信息可见。
- 创建/恢复草稿、筛选、编辑面板、删除和发布流程可操作。
- 自动保存状态、错误定位、修订冲突和导入差异反馈正确。
- 其他四类资料可以预览、下载和上传替换。

回归验证：

- Python 全部单元与集成测试。
- 前端全部 Vitest 测试和生产构建。
- Docker Compose 配置、PostgreSQL 新表创建和 API 健康检查。
- PC 端 Chrome 视觉验收，至少覆盖 1440×900 和 1920×1080。
- 使用脱敏数据验证草稿发布后批次计算、待处理定位补充和导出仍保持现有规则。

## 12. 交付边界

本轮完成后，库位/排仓具备完整的网页维护和 Excel 整表替换能力；其余四类资料具备可理解的查看、预览、下载、替换和版本管理能力。完整业务数据仍以正式 `InputVersion` Excel 版本为边界，草稿不会绕开现有核心逻辑。
