# Codex 界面设计发现与探索规范

本文件按 SEEKWAY V2.1.0 适配 DeliveryNote；来源与项目差异见 [README](../../README.md#codex-规范接入)。

新建 Web 界面或原型、明显重设计，或界面方向不明确时必须读取。本文件负责设计决策；组件、令牌、布局和可访问性仍按项目 Web UI 规范执行。

## 1. 原则与适用范围

模型按上下文条件下的概率分布生成内容。提示中的“随机”、增加候选数量、提高温度或反复要求创新，都不保证均匀抽样或结构覆盖。模型能表达多种方案，也不代表一次生成会覆盖这些方向。外部采样只控制已定义选项的选择，无法补回遗漏的方向，也不保证设计质量。

空间定义、候选解释和筛选都须记录依据，避免各环节沿用同一种偏好。先确定任务和约束，再分别探索、筛选和比较；不得把生成概率、模型自报概率或熟悉程度当作设计价值。

| 任务 | 执行范围 |
| --- | --- |
| 现有模式内的局部修复 | 沿用现有设计，验证受影响状态；不要求多方案和采样 |
| 新页面已有适用且经过验证的模式 | 说明任务、复用依据和差异后实施；有未解决的设计问题再展开探索 |
| 提供明确设计稿、要求还原 | 核对任务、状态和约束，按稿实现；冲突先确认，不擅自改成其他方向 |
| 只要求视觉改进且方向模糊 | 将用户描述的感受转为具体设计变量，比较构图、字阶、密度和视觉强调；保持已确认的业务与交互 |
| 新工作台、编辑器或明显重设计，结构与操作方式不明确 | 建立任务模型与设计空间，安排方向覆盖、筛选候选并验证任务原型 |

优先在对话和用户已授权的现有任务说明中记录设计。只有用户明确要求时才创建文档；需跨阶段复核时在同一记录中维护输入与决策，任务结束时清理本次无用临时产物。

## 2. 意图翻译与任务发现

1. 保留用户原话，为“高级”“科技感”“有设计感”等描述提出可能的解释，说明与当前产品的关系；不得要求用户掌握专业术语，也不得套用“高级必然黑白”等固定对应。
2. 说明每种解释对应的可观察变量，例如信息层级、字阶、留白、视觉噪音和操作强调，以及如何判断是否符合用户意图。
3. 了解目标用户、关键任务、使用频率、数据规模、操作环境、成功标准和现有品牌。只追问会影响方案的未知事项；偏好不明确时，用简短对比帮助用户判断。
4. 区分已确认事实、推测和待验证假设。不得借方案补充未经确认的业务能力，例如为了形成“AI 驱动”方向擅自增加自动决策。

所有候选保持相同目标、关键任务、数据和硬约束。更换产品目标不算同一任务的设计发散。

## 3. 约束与设计空间

### 3.1 先核对约束

- 业务规则、权限、安全、可访问性和已确认的品牌要求属于硬约束。
- 默认侧栏、页面骨架、信息密度等属于基准方案，除非项目已明确规定不可改变。
- 已确认采用的现有布局是局部任务的边界；用户要求重设计时，先明确允许改变的部分。
- 探索中改变默认布局不代表获准采用。方向确认后，将差异同步到项目界面规范，再实现。

### 3.2 显式建立空间

按任务选择维度，不照搬固定表格。结构探索可涉及任务组织、信息架构、导航、工作区、操作路径和密度；视觉探索可涉及构图、字阶、节奏、材质和强调方式。每个维度与选项须标明来源：任务事实、既有基准、参考案例或待验证假设。

建立空间后必须检查：

1. 哪些默认前提尚无任务依据，例如“工作台必须有固定侧栏”。
2. 是否只列出了同一类界面的局部变体，是否遗漏时间、对象关系、队列、直接操作等与任务有关的组织方式。
3. 是否名称不同却有相同操作路径；选项之间是否重叠或互相依赖。
4. 哪些组合不成立，依据是什么；未验证的困难不能直接写成硬排除条件。
5. 某类方向是否因拆成更多选项而获得更多探索机会；须通过分组安排各类机会，不声称整个设计空间均匀。

采样前保留可审查的空间版本。发现遗漏、语义重复或错误排除时，修订空间并说明原因后重新运行；不得静默删除维度、修改配额或放宽硬约束。

## 4. 覆盖安排与程序采样

### 4.1 安排方向

保留一个符合任务约束的基准。完整探索还须覆盖不同结构、适用边界和挑战默认前提的方向，逐项写明要验证的问题。正交、边界和反先验是探索方法，不能证明模型偏差已消除。

正交方向须在重要任务或设计维度上产生有意义的差异，不要求数学上的独立；边界用来检查适用范围，反先验用来检验常见前提。限制常见模式只作用于相应探索分组，不成为全项目禁令。方法重叠时可复用方向，但须说明实际覆盖；不得用不合理方案凑数。

需要时，通过逆向探索反转可调整的默认方式，或通过反事实探索移除未经证实的前提；两者仍须保持同一任务和硬约束。按当前设计问题选择方法，无需每次全部执行。

候选数量是探索预算。先列出组合与操作路径，核对覆盖后再深化，不必为每个候选制作完整原型，也不固定“20 个必然筛成 3 个”。连续生成没有带来新的有效方向时，重新检查空间和约束，停止堆数量。

### 4.2 工具使用边界

本次规范接入不复制设计采样脚本或示例配置。需要探索时优先显式列举不同操作路径与覆盖范围，沿用现有设计作为基准；不得把模型自选的方案描述成均匀随机抽样。

确有程序采样需求时，先复用项目等价工具；不足时再评估 [V2.1.0 源仓库的设计探索工具](https://github.com/songtu2025/seekway-codex-standards/tree/v2.1.0/templates/design-exploration)，说明来源、许可、必要性和文件范围，确认后再引入。工具未接入前不写成本地可执行命令。

使用工具时保留真实输入、工具版本、种子、覆盖和不足项，示例假设须按当前任务重新核对。程序无法运行时如实采用显式列举，不编造种子、概率或运行结果。采样完成不代表设计通过，最终仍须验证关键操作和用户反馈。

## 5. 候选解释、筛选与用户比较

先将每个组合解释为简短方案，说明关键任务的入口、处理过程和结束方式，以及信息组织和反馈。逐项核对方案是否符合组合；无法解释时，记录问题并说明修订或淘汰理由，不悄悄换回基准。编码距离不能替代体验差异判断。

给用户展示前，按以下顺序筛选并记录依据：

1. 核对真实任务和硬约束，指出违反的具体要求。
2. 核对组合能否成立；区分确认不成立、实现成本高和仍待验证。
3. 合并实际任务路径或视觉表达重复的方案，编码不同也不例外；保留有价值的差异。
4. 分别评估可用性、新颖性、学习成本和实现成本，不用模型自评分或熟悉程度作唯一依据。
5. 保留有潜力但证据不足的方向，用最小原型验证疑问；不能仅因少见、偏离默认侧栏或描述不够流畅而删除。

复用当前任务说明，以候选编号记录组合、解释、保留或淘汰结论、具体依据和待验证项。改变输入后的记录须能区分版本，不能覆盖原结果后声称未改变空间。

最终展示多少方案，取决于有效方向；少于预期时说明原因。比较表须列出同一关键任务下的操作路径、主要结构或视觉差异、适用条件、代价和待验证问题，并附结构草图或最小原型。不得默认第一个方案最佳，也不得将偏好差异包装成客观评分排名。

## 6. 选定方向、视觉表达与验证

用户确认方向后，说明构图、字阶、密度、色彩强调、图像与动效如何表达用户期望的感受、服务于任务和受众，再落实到现有设计令牌与组件。保留清楚的视觉重点，避免无依据地套用同一种卡片、渐变或装饰组合；不以反常或装饰数量判断设计质量。

按 `docs/codex/frontend.md` 处理原型与合成数据，按 `docs/codex/workflow.md` 衔接接口契约和真实闭环。关键原型使用相同任务、数据和视口比较操作、查找、阅读、学习与错误恢复；记录用户反馈和仍未验证的假设。模型评审须引用这些依据，不能替代实际操作验证。

最终界面按项目 Web UI 规范检查视觉层级、一致性、各类状态、键盘、对比度和响应式，并对照选定方向核对实现。完成检查见 `docs/codex/verification.md`；未经原型或实际使用验证，不声称提升了业务效率或审美质量。

## 7. 依据与研究边界

- [Verbalized Sampling](https://arxiv.org/abs/2510.01171)：研究偏好数据的典型性偏差及生成多样性干预，不证明特定前端设计有效。
- [Examining and Addressing Barriers to Diversity in LLM-Generated Ideas](https://arxiv.org/abs/2602.20408)：研究生成固着和知识分区；具体效果受模型、任务及方法影响。
- [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)：评审模型存在位置、冗长和自我偏好等偏差，模型评价须结合独立证据。

本文件用覆盖安排、配置和筛选记录应对上述问题。实际设计效果仍须在项目中验证，不将研究结论视为所有模型的固定规律。
