# Codex 开发流程与项目边界

涉及非简单需求、代码结构、配置、依赖、部署、项目文档或生产边界时，必须读取本文件。发现与根规则冲突时先核对事实并确认处理方式，不擅自覆盖。

## 1. 项目技术与环境基线

本文件按 SEEKWAY V2.1.0 适配 DeliveryNote；来源、版本和项目差异见 [README](../../README.md#codex-规范接入)。

- 本地开发使用 Windows PowerShell；Linux/CI 使用 Bash，Python 3.11、Node.js 22，依赖以项目锁文件为准。
- 前端沿用 React 19、TypeScript、Vite、Ant Design 6、`@ant-design/icons` 6 和现有主题；使用 npm。
- 后端沿用 Python、FastAPI、Pydantic、SQLAlchemy、unittest、Ruff、Mypy 和项目统一迁移入口。
- 部署沿用 Docker Compose、Nginx 和 PostgreSQL；保留 SQLite 开发兼容行为。生产操作由部署负责人执行已确认的流程。
- 现有目录、框架、组件库、数据库和部署方案保持兼容；不为符合公司默认目录引入 Alembic、pytest、图表库或其他依赖。

## 2. 项目目录与职责

| 项目路径 | 职责 |
| --- | --- |
| `delivery_note` | Web、CLI、Worker 共用的业务核心 |
| `delivery_note/web` | API、鉴权、模型和后台维护 |
| `frontend/src` | React PC 操作界面 |
| `tests` | 后端和核心业务测试 |
| `scripts`、`frontend/scripts` | 已有检查、发布和维护工具 |
| `docs/codex` | 按任务读取的开发与验证规范 |
| `docs/web-ui-standard.md` | 界面通用规则与专项索引 |
| `.github/workflows/ci.yml` | 项目持续集成检查 |

业务与架构边界以根目录 README 和 AGENTS.md 为准。内部按实际职责组织模块，不为凑结构创建空壳、转发层或重复规则。前后端命名应能追踪同一业务流程，优先复用已有实现和调用链。

## 3. 规则加载、合并与升级

### 3.1 加载与优先级

1. 系统、平台、安全与权限边界始终生效；在此范围内依次遵循用户目标、项目规则、任务命中的专项规范和现有实现。
2. 从项目根目录到工作目录的规则按作用域生效；同一目录有 `AGENTS.override.md` 时，普通 `AGENTS.md` 不会同时加载。不得擅自新增、删除或替换覆盖文件。
3. 普通专项 Markdown 不会自动加载；根规则用“触发条件 + 路径”建立索引，只读取命中的文件。嵌套规则只补充目录特有要求，不重复父级规则。
4. 当前项目优先复用已有规则文件；不得整文件覆盖有效业务、安全、兼容和验证规则。冲突或证据不足时保留原规则，说明影响并确认。
5. 根规则以 100 行以内为维护目标，不得为缩短文件删除有效约束。加载机制以 [OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 为准。

### 3.2 项目差异与合并

- 项目实际技术栈、目录、包管理器、测试框架、迁移入口和已确认设计系统优先于公司默认选型。
- 安全、权限、数据保护和破坏性操作的底线不得通过项目差异放宽。
- 含义相同的规则只维护一个事实来源；检查命令集中在 README，专项规范描述触发条件和验收要求。
- 项目差异须改入对应条款并在 README 汇总，不得留下相互矛盾的强制要求。无法确认的历史规则不自行删除。
- 既有代码问题按实际影响逐步处理，不将历史不良写法固化为永久例外，不因规范升级全仓重写。

### 3.3 升级与验证

1. 修改前检查 Git 状态、现有规则及覆盖文件，核对来源和回退条件，并说明文件范围、适用差异和验证方法。
2. 从规范源仓库通过 HTTPS 获取已发布版本的标签 ZIP，在项目外核验；使用主分支或受控离线包前须明确来源并确认。完整规范仓库不嵌套到业务项目。
3. 使用版本管理并保护现有未提交改动；规则文件修改前在项目外保存本次副本。恢复时只处理本次文件，先核对期间新增的改动。
4. 将上游变更分成适用、不适用、已存在和冲突，只合并适用且缺失的内容。获得方案确认后实施，已获确认的范围不重复索要许可。
5. 在 README 记录规范基线、来源提交、实际接入日期、版本控制状态、项目差异和加载验证结果；未验证时写明待验证。
6. 接入后从业务项目根目录新建聊天，核对实际加载的规则与任务索引；完成标准见 [验证规范](verification.md)。业务产品发布不套用规范源仓库的版本发布流程。

## 4. 分层 AI 协作开发流程

流程产物优先在对话中说明；只有用户明确要求时才创建文档。维护任务已授权的规范文件或现有说明时，限定必要范围，不额外生成任务计划、审计报告或学习文档。

### 4.1 任务分级

| 级别 | 判定 | 必要流程 |
| --- | --- | --- |
| 简单 | 现有模式内的局部修改，不新增业务规则、数据、接口或高风险影响 | 目标、验收、影响、修改和检查 |
| 标准 | 新页面、接口、数据字段或业务操作 | 需求定义、必要设计、验证策略、真实闭环和验收 |
| 高风险 | 新系统、跨系统流程、敏感数据、认证权限、数据迁移、不可逆操作、明确容量要求或部署变更 | 标准流程，加安全、隐私、容量、迁移、监控、发布和回滚设计 |

AI 须选择能覆盖风险的最轻级别并说明理由；无法判定时按更高一级处理并请求确认。

### 4.2 完整生命周期与确认门

| 阶段 | 核心产物 | 通过条件 |
| --- | --- | --- |
| 发现问题 | 真实问题、现状、用户、约束和改进价值 | 确定值得解决 |
| 定义需求 | 目标、范围、不做事项、成功指标和验收标准 | 用户确认需求 |
| 业务与产品设计 | 业务、用户、数据、页面、系统和权限方案 | 关键规则和目标流程已确认 |
| 原型与可行性验证 | 前端 Demo、技术验证或直接实现决策 | 最大不确定性已降低 |
| 技术与任务计划 | 修改范围、顺序、风险、回滚和验证方案 | 非简单任务获得实施确认 |
| 增量开发 | 先打通最小真实闭环，再扩展功能 | 代码、数据和交互一致 |
| 综合验证 | 技术检查、用户验收和风险结果 | 达到交付条件 |
| 发布、运营与改进 | 发布记录、监控、反馈、效果判断和后续动作 | 达标、改进、回滚、暂停或下线决策明确 |

### 4.3 从现有做法到目标系统

用户描述的现有操作是理解问题的证据，不是默认的系统方案。标准和高风险任务必须：

1. 记录现状流程 `As-Is`，逐步追问目的、输入、输出、角色和异常。
2. 将每个步骤区分为必须保留的业务规则、法律或组织硬约束、现有工具的限制和补救动作、可调整的操作习惯。
3. 用 Web 系统能力重新设计目标流程 `To-Be`，不得机械复制导出、复制、重复录入和人工传话等旧工具限制。
4. 对保留、变更和删除的步骤说明理由，获得用户确认后再进入详细设计。

### 4.4 设计视角

| 视角 | 必须回答 |
| --- | --- |
| 目标与范围 | 为谁解决什么问题，什么结果算成功，明确不做什么 |
| 参与者与职责 | 谁使用、审批、维护或提供外部能力 |
| 业务流程与规则 | 业务如何触发、流转、变更状态和处理异常 |
| 用户旅程与操作 | 用户从哪里进入、做什么、得到什么反馈 |
| 领域与数据 | 核心对象、唯一事实源、状态、来源、去向和生命周期 |
| 信息架构与页面 | 导航、页面关系、字段、操作和各类页面状态 |
| 系统与接口 | 前后端职责、接口、外部集成、事件、定时任务和失败边界 |
| 验收与度量 | 功能如何验收，业务效果如何度量，何时复查并采取什么动作 |

安全、隐私、权限、审计、可访问性、性能、可用性、容量、兼容性、成本、许可证和维护能力是横跨各视角的约束；只展开与当前任务有关的内容。

新建 Web 界面或原型、明显重设计，或方向不明确时，按 `docs/codex/interface-design.md` 确定探索范围。需要探索时，先核对覆盖与筛选依据并确认方向，再深化原型、进入生产实现；成熟模式内的任务按该规范轻量执行。

### 4.5 原型、技术验证与真实闭环

1. 按最大不确定性选择前端 Demo、技术验证或直接实现，不得因为 Demo 直观就忽略更高的集成、数据或安全风险。
2. 新系统、新流程、多角色交互或界面不确定性高时，优先使用足以验证操作流程的 Demo。
3. 原型只需验证高风险假设，不默认是生产代码，也不代表功能完成。
4. Demo 确认后必须先定义数据和接口契约，打通一个包含真实页面、接口、业务逻辑和数据读写的最小端到端流程，再扩展其他功能。

### 4.6 PDCA 闭环

1. `Plan`：记录改造前基线、目标、验收标准、可量化指标、数据来源、负责人和复查时间；不适用时说明理由。
2. `Do`：执行验证、开发和发布，保留与目标和方案对应的可验证结果。
3. `Check`：对照验收标准、用户反馈和业务指标检查技术结果与实际效果。
4. `Act`：根据证据明确保留、优化、回滚、暂停或下线，并将未解决问题进入下一轮计划。

简单任务以验收标准完成最小 PDCA；有可观测业务效果的功能必须说明上线后如何复查。

## 5. 开始开发前

修改代码前必须：

1. 按 `AGENTS.md` 索引读取相关专项规范，并阅读 README、需求、相关代码和测试。
2. 判定任务级别，检查调用链、现有实现和可复用能力。
3. 优先复用已配置的工具和技能。根目录存在 `.codegraph/` 时先用 CodeGraph 定位代码；无相关结果时再定向搜索。新增辅助工具、技能或配置前说明必要性、来源、许可、权限和不配置时的处理方式；同一任务只询问一次，未经确认不安装。
4. 对非简单且可能已有通用解法的需求，可以只读调研开源项目，并记录候选方案、来源、许可证、维护状态、安全风险、适配范围和集成成本。
5. 复述已确认的需求、目标流程、验收标准和不做事项。
6. 列出修改文件、影响内容及数据库、认证、权限、配置、依赖和部署影响。
7. 说明风险、回滚方式和验证方案，非简单任务获得确认后再修改。

开源调研只用于需求讨论和方案比较。复制代码、引入依赖或改变技术方案前，必须说明来源与影响，并按本规范获得确认。

涉及 Web 界面时，还须读取 `docs/codex/frontend.md` 和 `docs/web-ui-standard.md`，再按触发条件读取布局、表单或数据专项规范；缺失时报告，不假设项目外模板可用。检查已有令牌、组件、布局和相似页面，明确设计来源、目标视口及页面状态。改变现有设计系统前必须确认。

## 6. 修改范围

修改边界以根目录 `AGENTS.md` 的业务规则和实施边界为准。新增或修改业务逻辑时补充必要测试；发现无关问题只在对话中报告，不顺带修改或创建额外文档。未经确认不得删除现有功能、接口、字段或数据，也不得在多处维护同一业务规则。

## 7. 安全与生产边界

不得主动读取、生成、提交或传播真实凭据、生产环境变量、未脱敏业务数据，以及含敏感信息的数据库、日志、上传文件和导出结果。

可以读取和处理：

- 认证相关的代码、字段名和配置结构。
- 不包含真实凭据的 `.env.example` 和占位值。
- 测试数据、模拟数据和已经脱敏的数据。
- 用户明确提供且不包含真实敏感信息的需求附件、示例文件和设计资料。

允许使用不显示命中值的工具扫描源码和提交记录。发现真实敏感信息时须停止处理并提醒用户，不得复述其值。生产数据库和生产迁移只能由部署负责人操作。

## 8. 项目文档

创建或维护项目时，README 至少包含：

- 项目用途、适用范围和明确不做的事项。
- 技术栈、系统架构和关键业务规则。
- 本地启动、测试和构建方式。
- 部署文档入口。

修改对外行为、API 或数据契约、配置项、启动与检查命令、部署方式时，须核对并同步受影响的项目文档和示例。纯内部实现变化且文档内容不受影响时，不必为凑同步而修改文档。文档与实现冲突时，先对照已确认的需求和契约判断错误方；证据不足时请求确认，不得直接按当前代码改写文档。

项目产品、公司规范和模板各有版本号，应分别标明来源与发布状态，不要求数字相同。工作版本与已发布版本须明确区分；同一发布版本的文档声明须与对应的包元数据、标签或发布产物一致。不一致时先核对实际发布状态，不得仅修改文案掩盖差异。

根目录 `AGENTS.md` 至少包含业务边界、Codex 修改规则、禁止修改内容、专项规范索引、必须执行的检查以及数据和 Git 安全要求。重要业务规则不得只存在于聊天记录或个人记忆中。
