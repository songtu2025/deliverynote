## 1. 记录目的

本文仅保存待处理审校批量功能的讨论结论，方便以后出现明确需求时继续评估。它不是已批准需求、实施计划或生产功能说明。

在重新启动开发前，应先根据真实操作确认主要痛点属于以下哪一种：

1. 多条记录结论相同，但业务员必须逐条打开和保存；
2. 多条记录需要填写相同站点、仓库或其他字段；
3. 判断依据分散，导致单条审校本身耗时；
4. 业务员需要标记“已经审阅，但暂时不处理”。

只有第一种痛点适合本文提出的第一版“批量确认可导入”。其他痛点应分别考虑批量赋值、信息聚合或独立审阅状态，不能用一个笼统的批量按钮代替。

## 2. 计划解决的痛点

当多条待处理记录已经具备完整信息，并且业务员对它们作出的结论相同时，当前逐条执行“打开记录、核对、确认可导入、保存、切换下一条”会产生重复操作。

批量功能的目标是把这种操作收敛为：

```text
显式勾选 → 集中预览 → 服务端复核 → 全部提交或全部拒绝 → 刷新结果
```

预期收益：

- 减少重复打开抽屉和保存；
- 避免遗漏散落在不同来源文件中的同类记录；
- 以一个原子操作完成多条确认，避免用户难以判断部分成功结果；
- 统一记录审计信息；
- 每次批量操作只统一失效一次已有导出结果。

该功能不解决需要逐条作出不同业务判断的记录，例如站点仍然不唯一、字段缺失或数量需要分别拆分。

## 3. 建议的第一版范围

第一版只提供一个主要动作：

> 批量确认可导入

不提供“批量继续保留待处理”。当前模型中，继续保留待处理不会减少未完成数量，也不会形成新的有效业务结果。如果以后确实需要避免多人重复审阅，应单独设计“已审阅待处理”状态。

以下记录不得直接参加批量确认：

- 站点为空或仍包含多个候选站点；
- 目的仓、供应商编码或 SKU 不完整；
- 已经存在人工拆分或审校草稿；
- 已经处理完成；
- 数量不合法；
- 不属于当前批次。

用户只能操作显式勾选的记录。第一版不隐式选择隐藏记录，不跨批次处理，也不以一个值覆盖不同记录原有字段。

## 4. 建议的页面交互

待处理审校表格增加勾选列和固定批量操作栏。操作栏展示：

- 已选择记录数；
- 涉及来源文件数；
- 合计待处理数量；
- 各异常原因数量；
- “预览批量确认”操作。

不符合条件的记录应禁用勾选，并直接说明原因，例如“请先选择唯一站点”或“已有人工拆分，请单独处理”。

确认面板至少展示：

- 即将处理的记录数和数量；
- 涉及的来源文件；
- 异常原因分布；
- 正常采购分配、超出量以及已有的超收额度信息；
- 将采用的目的仓、SKU 和唯一站点；
- 已有导出结果将失效、需要重新生成的提示。

页面文案应明确这是“人工确认可导入”，不能让用户误以为系统重新运行了采购匹配或超收规则。

## 5. 不同异常原因的建议口径

| 异常原因 | 第一版建议 |
| --- | --- |
| 未找到可交货采购需求 | 字段完整时允许显式选择，审计标记为人工确认 |
| 超出采购未交量 | 允许显式选择，预览展示正常分配量和超出量 |
| 产品信息站点不唯一 | 不允许直接批量确认，必须先确定唯一站点 |
| 超出允许超收量 | 允许显式选择，但预览必须突出正常量、额度使用和超出量 |

该批量操作只复用现有人工审校能力，不重新计算或扣减采购余额，不改变文件处理顺序、仓库优先级或超收规则版本。

## 6. 建议的服务端约束

如果以后实施，应使用批次级接口，不应由前端循环调用单条保存接口。

服务端应在同一事务中：

1. 锁定批次；
2. 确认批次已计算成功，且没有导出任务正在运行；
3. 按确定性顺序锁定全部选中记录；
4. 重新验证记录归属、状态、必填字段、唯一站点和已有拆分；
5. 调用现有共享拆分投影逻辑，不复制采购匹配代码；
6. 验证每条记录及批次结果的数量守恒；
7. 统一失效已有导出；
8. 写入审计记录；
9. 提交事务。

采用全有或全无的原子语义。任意一条记录在预览后被其他用户修改或不再符合条件时，整次操作不写入，并向页面返回具体冲突原因。

## 7. 审计建议

每次批量操作使用统一操作编号，并保留：

- 操作人和北京时间；
- 批次、记录及来源文件；
- 异常原因分布和总数量；
- 每条记录的处理前后状态；
- 是否属于规则之外的人工确认；
- 导出失效情况。

每条待处理记录仍应能够追溯自身变化，不能只保留一个无法定位具体记录的汇总事件。

## 8. 明确不纳入第一版

- 跨批次批量操作；
- 批量任意拆分数量；
- 批量覆盖 SKU、站点、目的仓或供应商编码；
- 覆盖已有拆分或审校草稿；
- 重新运行采购匹配或重新扣减采购余额；
- ERP 回写；
- 新增复杂审批流或权限体系；
- 手机端适配。

现有 `operator` 和 `admin` 的审校权限保持不变，不因批量能力引入新的角色模型。

## 9. 实施前必须补充的验证

如果未来确认开发，应先新增或定位测试，至少覆盖：

- 多条符合条件的记录一次确认成功；
- 任意一条不合法时全部回滚；
- 站点不唯一时拒绝；
- 已有拆分时拒绝覆盖；
- 两个用户并发处理同一记录；
- 导出运行中禁止修改；
- 成功后统一失效导出；
- 审计信息完整；
- 始终满足 `交货总量 = 可导入总量 + 待处理总量`；
- 不影响共享采购余额、文件顺序、仓库优先级、锁仓逻辑、CLI 和 A:G 导出。

## 10. 重新讨论时的决策问题

重新启动该需求前，应使用真实操作反馈回答：

1. 一次通常需要重复确认多少条记录？
2. 哪些异常原因最常得到相同处理结论？
3. 最大痛点是重复保存、重复填写字段，还是查找判断依据？
4. 是否确实需要批量突破超收规则，还是此类记录必须逐条确认？
5. 是否需要“已审阅待处理”状态来避免重复审阅？

未获得这些答案前，不建议直接进入实现。
